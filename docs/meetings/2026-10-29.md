## 2. What the commit changed

Three correctness defects in the Student D TOR pipeline, all of which altered the reported
result, plus the reproducibility of the notebook.

### 2.1 Cross-validation was splitting by coin, not by time

`TimeSeriesSplit(n_splits=5, gap=7)` was given the **rows** of the modelling frame. That frame
is a panel: all eight tokens share every date, and the rows arrive grouped by token. The folds
therefore cut the panel **by coin** — every fold's validation set spanned the same date range as
its own training set — and `gap=7` purged seven *rows*, under one calendar day of an eight-token
panel, instead of the seven days the label horizon requires.

The split is now taken over the distinct **dates** of the training period and mapped back to rows
(`purged_date_folds`). The folds are an expanding window ordered in time, all eight tokens appear
on both sides of every fold, and each seam purges eight days. The previously reported CV figure of
0.4219 was measuring cross-coin generalisation, not forecasting.

**This is a general trap for every model in this project, not just TOR** — see §3, D12.

### 2.2 Early stopping was reading the fold it was scored on

Each trial early-stopped on `eval_set=fold_valid` and was then scored on that same fold, so the
round count was selected by looking at the rows the trial was judged on. `n_estimators` is already
part of the Optuna search space, so early stopping was removed rather than relocated.

### 2.3 macro-F1 was averaged over a different number of classes each time

`_score` averaged over whichever labels happened to be present. `Strong Sell` is ~3% of the data
and is absent from the test window entirely, so the model was scored over four classes while the
per-token table used a different label set for each coin. All F1 figures now average over the fixed
five labels, which is what makes the model, the four baselines and the per-token table comparable.
`metrics.json` records `labels_in_test` so the absence is visible rather than hidden.

### 2.4 The notebook was not reproducible

It fetched live from Kraken three times per run. Kraken serves only the latest 720 candles, so the
window slides daily and the numbers in the notebook, in `metrics.json` and in the report drifted
apart on every re-run; a run spanning midnight UTC used two different datasets within one notebook.
It now reads the committed snapshot, as Student B's notebook does, with `REFRESH_DATA = True` to
re-download. `deterministic=True, force_row_wise=True` are set, as README §14 already claimed.

### 2.6 Other fixes

- `metrics.json` reported `n_estimators=259` while the saved artefact had 216, because the final
  fit overrode it. `/model-metadata` now advertises exactly what was fitted.
- `OS` was a model input with no entry in `feature_sources` and no mention in the feature-selection
  section. Its provenance, and why it is not leakage, are now documented where the set is chosen.
- log-loss raised on a shape mismatch if a rating was absent from training (e.g. `--tokens BTC`).
- `num_leaves` is searched in `[8, 2**max_depth]`; above that it is inert.
- Kraken's result key is matched against the mapping agreed in CONTRACT.md §3 instead of taking
  whichever key arrives first; de-duplication now happens after sorting.
- Every quoted figure in the notebook is interpolated from the run instead of transcribed. The
  previous prose had drifted: it described 2,000 estimators with early stopping at patience 100,
  a MedianPruner, 60 trials and six features — none of which the code did.
- The notebook is renamed to the student-ID form, and the name and ID fields are filled in.
- README gains the Student D results section; the Makefile gains the five targets README already
  documented (`features`, `evaluate`, `train`, `predict`) plus `make tor`.
- `make lint` and `make test` pass — 40 tests, up from 31.

## 3. Proposed decisions — awaiting group acknowledgement

- **D12 (proposed, affects all four models):** when applying `TimeSeriesSplit` to the pooled
  eight-token panel, split on the distinct **dates**, not the rows, and set the gap in days.
  Splitting rows cuts the panel by coin and reports a CV score several points too high.
  Students A, B and C should each check their own tuning code against this. Recorded in
  README §7 *Shared experimental conventions*.
- **D13 (proposed):** classification metrics are averaged over the **full** label set, including
  ratings absent from a split, so figures are comparable between models and between students.
- **D14 (proposed):** enable branch protection on `main` as CONTRACT.md §10 already requires, and
  add the missing §11 escalation clause to CONTRACT.md — or remove the reference to it from
  README §13.
- **D15 (proposed):** retrospective acknowledgement of the direct push described in §1.
